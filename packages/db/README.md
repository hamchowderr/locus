# @locus/db

Drizzle schema and migrations for the two kinds of database. Design: vault notes
`Locus Data Model` and `Locus Phase 0`.

| Database | Holds | Migrated by |
|---|---|---|
| **control** (one) | Better Auth's tables, the client registry (`location`), staff client access (`member_location`), site index, the three connections (each names its credential by path), agencies' credentials sealed with AES-256-GCM (`secret`, via `DbSecretStore`), audit log, AI usage metering (`usage_event`, its monthly rollup `usage_month`, `usage_limit`, `usage_alert`), each tenant's schema state | Drizzle's migrator — `migrateControlDb` |
| **tenant** (one per client) | `site_file`, `site_version`, `generation_run`. Never any GHL data | our runner — `migrateTenants` |

## Changing a schema

```
pnpm --filter @locus/db generate         # writes migrations/control and migrations/tenant
```

`generate` also embeds the tenant migrations in `src/generated/tenant-migrations.ts`: tenants are
migrated at run time inside the deployed app, which ships code but not this package's files. A
test fails if the embedded copy and `migrations/tenant` disagree.

A test fails if a schema change has no migration. `src/control/auth-schema.ts` is generated by
Better Auth's CLI (`pnpm --filter @locus/auth generate:schema`) — never edit it; add anything it
lacks as a custom migration (see `0001_invitation_inviter_index.sql`). Every foreign key is
indexed, and a test enforces that: Turso bills rows scanned.

## Clients

- `provisionLocation` creates the client's database, registers it, migrates it, marks it active.
- `offboardLocation` deletes the database, then the row (which cascades).
- `migrateTenants` walks every client **from our registry** and applies what each is missing.
  It stores the full applied hash set per client, so a migration skipped in the middle is
  detected and repaired — Drizzle's migrator only checks the newest and would miss it. One
  client failing is recorded in `location_schema_version.last_error` and never stops the rest.

`TenantProvisioner` creates, grants and deletes a client's database
(`provisionerFromEnv`, `LOCUS_PROVISIONER=local|turso`):

- `TursoProvisioner` — production. The Turso Platform API with `TURSO_ORG`, `TURSO_GROUP` and
  `TURSO_API_TOKEN` (a token limited to `db:create`, `db:delete`, `db:mint-token`). Each client
  gets an empty database in the group, and `provisionLocation` migrates it straight away, so
  there is no template to keep current. The hostname is always the one Turso returns. Tokens
  name one database and always expire (Turso can't revoke a single token). Deleting is safe to
  repeat.
- `LocalProvisioner` — development: one SQLite file per client. It **isolates nothing**; a test
  that claims to prove a tenancy boundary must run against Turso:
  `pnpm --filter @locus/db test:live` with the three `TURSO_*` values (a token for one client is
  refused by another's database).
